# Building MSap

## Quick Start

```bash
cd <path-to-msap>
./build.sh                  # Builds for this Mac's architecture
open build/msap.app         # Launch the app
```

Run `./build.sh --help` for the full set of options.

## Requirements

- macOS 12.0 or newer
- Apple Silicon (ARM64) or Intel (x86_64)
- CMake 3.20+ (typically via Homebrew: `brew install cmake`)
- Xcode command line tools: `xcode-select --install`
- Full Xcode, for `./build.sh --xcode` only. The command line builds do not
  need it. Point the tools at it with
  `sudo xcode-select -s /Applications/Xcode.app`.

## Building for Different Architectures

```bash
./build.sh              # this machine's own architecture - the default
./build.sh --arm        # Apple silicon, arm64
./build.sh --intel      # Intel, x86_64
./build.sh --universal  # One fat binary that runs on either Mac
```

The `ARCH`, `BUILD_DIR` and `CONFIG` environment variables still work and
override the flags.

The default is the host architecture alone, from `uname -m`, because it
roughly halves the build time. That means `./build.sh` produces an arm64 binary
on Apple silicon and an x86_64 one on an Intel Mac, with nothing to pass by
hand. That is the right setting for day to day work, but **a single
architecture build cannot catch the places where the two disagree**, and there
are real ones. `BOOL` is
`bool` on arm64 and `signed char` on x86_64, so a C++ member function pointer
written as `BOOL (Panel::*)(std::string&)` binds happily on Apple silicon and
fails to compile on Intel. Always run `./build.sh --universal` before moving
the source to an Intel Mac or cutting a release.

To check what you actually produced:

```bash
lipo -info build/msap.app/Contents/MacOS/msap
```

`./build.sh` prints this for you at the end.

On Apple silicon the Intel half can be exercised without leaving the machine,
provided Rosetta is installed:

```bash
arch -x86_64 build/msap_model_tests
arch -x86_64 build/msap.app/Contents/MacOS/msap
```

## Building and Debugging in Xcode

There is no checked in `.xcodeproj`. CMake generates one on demand:

```bash
./build.sh --xcode
open build-xcode/msap.xcodeproj
```

Pick the `msap` scheme and Run. Breakpoints, the view debugger and Instruments
all work, and the scheme is generated by CMake so it is present the first time
the project is opened. The generated project builds both architectures; choose
one in Product > Destination, or edit the scheme, to debug a single slice.

**Edit `CMakeLists.txt`, never the project.** Anything changed inside Xcode's
project settings is discarded the next time the project is regenerated. Two
settings already exist there for this reason:

- `XCODE_ATTRIBUTE_CLANG_ENABLE_OBJC_ARC` - the Xcode generator ignores the
  `$<COMPILE_LANGUAGE:OBJCXX>` generator expression that carries `-fobjc-arc`
  on the command line build, and would otherwise compile the ARC code under
  manual retain and release.
- `XCODE_GENERATE_SCHEME` - writes the shared scheme.

## CMake Options

`build.sh` is a thin wrapper. To drive CMake directly:

```bash
cmake -S . -B build \
  -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_OSX_ARCHITECTURES="arm64;x86_64" \
  -DCMAKE_OSX_DEPLOYMENT_TARGET=12.0
cmake --build build
```

Add `-G Xcode` to generate the project instead of makefiles. Note that
`CMakeLists.txt` defaults `CMAKE_OSX_ARCHITECTURES` to `arm64;x86_64`, so a
plain `cmake -S . -B build` produces a universal binary; it is `build.sh` that
narrows this to the host architecture for speed.

## Troubleshooting

### "No CMAKE_OBJCXX_COMPILER could be found" with `--xcode`

`xcodebuild` cannot load one of its plug-ins, so CMake cannot identify the
compiler. Repair the Xcode installation:

```bash
xcodebuild -runFirstLaunch
```

### "Xcode license" error
Accept the Xcode license:
```bash
sudo xcodebuild -license accept
```

### CMake not found
Install via Homebrew:
```bash
brew install cmake
```

### Command line tools outdated
```bash
xcode-select --install
```

## Build Directory Structure

```
build/                      Command line build, ./build.sh
├── CMakeCache.txt          CMake configuration
├── CMakeFiles/             Generated build system files
├── msap.app/               macOS application bundle
│   └── Contents/
│       ├── MacOS/msap      Executable binary
│       ├── Resources/MSap.icns
│       │                    Generated application icon
│       ├── Resources/icons Toolbar artwork and source msap.png
│       └── Info.plist      App metadata
├── libmsap_core.a          Analysis core library (static)
├── msap_model_tests        Test executable
├── msap_fft_bench          Benchmark executable
└── Makefile                Unix Makefiles generated build system

build-xcode/                Xcode build, ./build.sh --xcode
├── msap.xcodeproj/         Generated project and shared scheme
└── Debug/msap.app          Products land under the configuration name
```

Both directories are generated and can be deleted at any time.

## Minimum macOS version

`CMakeLists.txt` sets `CMAKE_OSX_DEPLOYMENT_TARGET` to 12.0 and the bundle
declares a matching `LSMinimumSystemVersion`, so the Finder refuses to launch
the app on anything older instead of failing with a missing symbol. The two
values come from the same place; change the CMake one and the plist follows.

Nothing in the source uses an API newer than 12.0. That is enforced by the
compiler rather than by inspection: clang's `-Wunguarded-availability-new` is
on by default, so reaching for a later API against a 12.0 deployment target is
a warning, and the build is warning clean. If you add one deliberately, wrap it
in `if (@available(macOS 13.0, *))` and keep a 12.0 path.

12.0 is a deliberate choice, not the compiler's minimum. The code itself only
reaches macOS 11.0, in three places: `setAllowedContentTypes:` and `UTType` in
the open and save panels, and the `imageWithSystemSymbolName:` last resort in
the toolbar icon loader. Monterey is picked because it is a stable release that
still covers every Mac Apple supports, Intel included, so there is no reason to
carry pre-11 fallbacks. Lowering to 11.0 would cost nothing today; going to
10.15 would mean swapping in the deprecated `setAllowedFileTypes:`, guarding
the SF Symbol call, and dropping the UniformTypeIdentifiers link.

**Not the same thing as being tested.** A 12.0 deployment target guarantees the
app links and starts; it does not prove the UI behaves. If that matters, run it
on the oldest system you care about.

## Moving the source to another Mac

`build/` and `build-xcode/` hold absolute paths and compiled objects for the
machine that produced them. Do not copy them; they will not work and CMake may
reuse their stale cache. Copy everything else and configure fresh:

```sh
rsync -a --exclude build --exclude build-xcode ~/projects/msap/ user@host:~/projects/msap/
```

Then on the target machine:

```sh
cd ~/projects/msap
./build.sh
```

On an Intel Mac `./build.sh` produces an x86_64 binary; `uname -m` reports
`x86_64` and `build.sh` follows the host. Nothing needs to be passed by hand.

If a copied build directory does get in the way, `./build.sh --clean` removes
it before configuring.

## Continuous Integration

The portable test suite runs on any platform (macOS, Linux):
```bash
cmake -S . -B build_test
cmake --build build_test
ctest --test-dir build_test
```

If tests pass on Linux (without `src/MsapApp.mm`), the core analysis layer has not been corrupted by UI code.

## Notes

- The app uses only system frameworks (Cocoa, CoreGraphics, CoreText,
  AudioToolbox and UniformTypeIdentifiers)
- No external dependencies or package managers required
- Source is all C++17 and Objective-C++
- Cross-platform portable core verified via Linux builds
